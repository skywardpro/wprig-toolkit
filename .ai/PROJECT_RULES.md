## 💻 Project-Specific Coding Patterns

<!--
Agent: Document the custom architectural habits and patterns you and the developer are establishing in this repository (e.g., custom hooks, naming standards, specific APIs to use or avoid).
-->

- **Custom PHP Patterns:** Optional third-party JS library wrappers live under
  `inc/WP_Rig_Toolkit/{Name}/Component.php` — one level deeper than stock WP Rig
  components, so `Theme::get_default_components()`'s auto-discovery does not pick them up.
  They're toggled via `ENABLE_*` constants in root `functions.php`, registered through
  the `wprig_theme_components` filter in `functions/_functions-toolkit-components.php`.
  Follow this pattern for any new optional feature; don't add a fixed array entry to
  `Theme.php` directly.
- **CSS Class Naming:** BEM (Block Element Modifier). Avoid deep nesting (keep under 3 levels).
- **CSS Architecture:** **Not PostCSS-only** — this is a mixed pipeline. The main
  `global.css` import chain is PostCSS/LightningCSS (custom properties, custom media
  queries), but the spacing-system, typography-system, and the vendored
  `_bulma-barebone` framework under `assets/css/src/framework/` are Sass-sourced and
  built through dedicated `npm run build:*` commands, not through the main `build:css`
  pipeline. Check which system a given partial belongs to before editing it.
- **SVG icons:** Two systems coexist — individual SVGs read via
  `wp_rig()->get_svg_icon()`, and a generated sprite (`npm run build:svg-sprite`) read
  via `wp_rig()->get_svg_icon_from_sprite()` / `the_svg_icon_from_sprite()`. Prefer the
  sprite for anything reused across templates.
- **Mandatory Skill Loading:** If asked to write, fix, or modify CSS, load the `styles`
  skill (`.ai/skills/styles/SKILL.md`) first — it documents which pipeline (PostCSS vs.
  Sass) a given file belongs to and the exact breakpoint names.
- **Block Development Guideline:** When asked for a custom block, ask which architecture
  is preferred (React-based vs. PHP-only), unless specified.

### 📅 2026-09-14 - Migrated build tooling and PHP architecture to wprig-master 3.4.2

- **Context:** This boilerplate had drifted from upstream WP Rig since forking around
  upstream tag `v3.1` (the exact commit where upstream itself replaced Gulp with a
  custom Node CLI) and had evolved its own build tooling, component set
  (`inc/WP_Rig_Toolkit/*`), SVG sprite system, and forms/spacing/typography systems
  independently since then. A prior, similar migration had already been done once on a
  sibling production theme (`wp-skyward`) — see that theme's `BUILD-MIGRATION.md` for
  the precedent methodology (pin an exact upstream commit, replace generic build
  concerns wholesale, protect project-specific PHP/templates, verify via build/bundle
  rather than lint).
- **Decision:** Adopted `inc/Theme.php`'s auto-discovery + `Asset_Provider` +
  `Versioning_Trait` from wprig-master wholesale; kept `WP_Rig_Toolkit/*` components on
  an explicit `ENABLE_*`-constant + `wprig_theme_components`-filter registration (they
  live one directory level too deep to be auto-discovered, which turned out to make this
  the safer choice anyway); reconciled build-tooling config files against the real
  upstream git history (a genuine git clone of this fork's own upstream lineage exists
  locally, with tags matching both the original fork point and the sync target, so real
  `git diff`/`git log -p` was used instead of comparing two disconnected snapshots); bumped
  PHP minimum to 8.1 project-wide; adopted the full `.ai/` knowledge base, `AGENTS.md`/
  `CLAUDE.md`, `.rig-config.json`, the Playwright/PHPUnit/Lighthouse test stack, the MCP
  doc server, and the Open Component Registry CLI, all customized for this repo's actual
  conventions rather than copied verbatim from stock WP Rig content.
- **Key Learning:** This project's `.prettier/plugin-php`-based formatting will silently
  strip the parentheses PHP <8.4 needs around `new ClassName()` when a fluent method
  chain follows immediately (`new Foo()->bar()` only parses on PHP 8.4+) — found this by
  discovering `.php-cs-fixer.php` itself didn't parse under the project's actual PHP
  8.1/8.2 runtime. Fixed by avoiding the fluent-on-`new` chain entirely (assign to a
  variable first) rather than fighting the formatter, since re-adding wrapping parens
  gets silently reformatted away on the next `prettier:fix` run (which the
  `.git-prehooks/pre-commit` hook runs automatically on every commit). The same
  fix-fight pattern hit `.stylelintrc`'s `at-rule-empty-line-before` rule vs. Prettier's
  CSS output (blank line right after an opening brace gets stripped) — same fix:
  adjust the rule/config, don't hand-edit the generated output.
- **Incident:** during the final step of this migration (moving the finished, git-tracked
  working copy into the live `wprig-toolkit` theme directory on Windows), a failed
  `mv`/`Move-Item` rename attempt silently deleted several root-level files and hidden
  directories (including all of `.git` and `.ai`) from the source before erroring out,
  while leaving most subdirectory contents untouched. Recovered by restoring untouched
  files from an unmigrated backup copy and re-applying every documented change by hand
  from this conversation's own record, then re-initializing git with a single fresh
  baseline commit (the incremental commit history from this migration was not
  recoverable). **Key Learning:** on Windows, prefer `robocopy` (without `/MOVE`/`/MIR`)
  or explicit copy-then-verify-then-delete-source over `mv`/`Move-Item` for large
  directory trees containing `.git` — plain rename/move of a directory tree with a
  `.git` folder is not safely atomic in this environment.
